### S1：管理员文件操作没有约束目录链接

位置：`src/BatteryCharge.App/CleanupService.cs:19`、`:26`、`:31`、`:32`；`src/BatteryCharge.App/LanguagePreferences.cs:40`、`:45`、`:46`；`src/BatteryCharge.App/app.manifest:7`。

程序全程以管理员身份运行。清理会处理 EXE 旁的配置，也会处理当前运行账户的 `%LOCALAPPDATA%\BatteryCharge` 遗留目录。`Path.GetFullPath` 只是路径规范化，没有验证最终目标；后续文件删除、枚举和保存会跟随父目录中的链接。

如果其他本地程序能把遗留目录或相关父目录改成指向其他目录的 NTFS junction/符号链接，用户确认“清理并退出”时，管理员进程可能删除链接目标中的同名配置。保存功能存在同类父目录问题，但它保存的是 EXE 目录的配置，不使用遗留目录。

影响有明确限制：清理仅删除 `settings.json` 和符合 `.settings-<32 位 GUID>.tmp` 命名规则的文件，不递归删除无关文件；保存仅写入受支持的语言 JSON，不接受任意文件名或任意文件内容。尚未确认能利用它完成 Windows 提权或任意文件删除。

Windows junction 的目录别名性质见[微软链接说明](https://learn.microsoft.com/en-us/windows/win32/fileio/hard-links-and-junctions)。结合代码和临时实验推断 Windows 上存在同类路径风险，最终影响需要 Windows ACL 实验确认。

建议：配置保存和用户目录清理由非管理员进程执行，把必须提权的驱动/任务操作放进范围受限的辅助进程。仍在管理员进程中进行的文件操作，应限制可信目录，校验路径各级的重解析点和写权限，并使用绑定目录句柄的操作防止检查后路径被替换。仅增加一次 `File.GetAttributes` 检查不能消除竞态。

修复验收应覆盖父目录链接、遗留目录 junction、检查后替换目录、操作失败保留配置，以及无关文件不被删除。

### S2：最高权限任务信任可被替换的 EXE

位置：`src/BatteryCharge.App/StartupManager.cs:18`、`:40`、`:55`；`src/BatteryCharge.App/StartupTaskDefinition.cs:31`、`:41`。

启用自动启动时只确认进程文件名是 `BatteryCharge.exe`，随后把当前进程路径写入 `HighestAvailable` 任务；没有校验目录和父目录是否允许普通权限进程改写，也没有限制目标必须处于受保护的本地目录。

如果部署目录可由其他本地进程改写，它可在应用退出后替换 EXE，等注册任务对应的管理员账户再次登录时获得管理员执行。当前的“路径不一致”提示比较路径字符串，不能发现同一路径下内容被替换，也不会在恶意 EXE 启动前阻止执行。

这不是已经验证的跨账户提权：同账户普通权限程序替换文件主要造成后续高权限执行和持久化风险；跨账户影响需要目标 ACL 允许攻击者写入。保护充分的安装目录能阻断该替换链。`HighestAvailable` 也不意味着以 SYSTEM 运行，任务权限由注册账户和运行级别决定，见[微软任务安全上下文](https://learn.microsoft.com/en-us/windows/win32/taskschd/security-contexts-for-running-tasks)。

建议：最高权限任务仅指向管理员保护的安装位置，校验 EXE、父目录和重解析点的有效权限。便携程序放在用户可写位置时，不应直接把该路径注册为长期高权限执行目标。需要更新时由受控的提权流程更新文件，并校验发布签名或可信来源；把校验哈希存入同一个可写目录无法建立信任。

Windows 验收至少应分别检查受保护目录、当前用户可写目录、其他账户可写目录及目录 junction。不能仅依据磁盘盘符或“Program Files”字符串判断安全。

### S3：预占单实例对象可以阻止启动

位置：`src/BatteryCharge.App/Program.cs:16`、`:19`、`:20`。

固定名称 `Global\BatteryCharge.Standalone` 被当作“真实实例已运行”的凭据。其他本地进程先创建同名对象时，程序可能直接退出，或因对象类型/权限不兼容在窗口出现前抛出异常。它没有验证对象持有者是真实的本应用实例。

微软明确说明[已知名称互斥锁可被预创建来阻止应用启动](https://learn.microsoft.com/en-us/windows/win32/api/synchapi/nf-synchapi-createmutexw)。这里确认的是本地拒绝服务风险，没有发现通过此对象执行任意指令的功能。显示窗口的事件不携带命令或文件路径。

建议：增加对象创建和打开失败的可读提示，不把“对象存在”直接视为可信实例；结合受保护的命名机制和受控通信校验实例。对象 ACL 能限制访问，但事后设置 ACL 不能解决攻击者先创建对象的问题，同 SID 进程的威胁也不能只靠用户 SID 名称消除。

另外存在多会话 bug：互斥锁是 `Global`，显示窗口事件却是 `Local`。在不同会话中打开程序，第二个实例可能退出，但唤醒不了第一个会话的窗口；对象 ACL 也可能导致访问失败。[微软命名空间说明](https://learn.microsoft.com/en-us/windows/win32/termserv/kernel-object-namespaces)确认两者作用范围不同。

修复应区分“整个设备上的驱动操作互斥”和“每个用户会话的窗口激活”。不能简单改成每用户一个实例锁，否则多个实例可能交错写入固件命令。

### S4：无上限的配置读取可拖垮启动

位置：`src/BatteryCharge.App/LanguagePreferences.cs:22`；`src/BatteryCharge.App/Program.cs:11`。

程序在初始化界面和单实例检查前完整读取配置，再解析 JSON。无用的大字符串字段也会被全部读取和解析。可修改配置的本地程序能制造很大的合法文件，造成启动迟缓或内存耗尽。当前回退只处理 IO、权限和 JSON 错误，没有从源头限制资源消耗。

建议：采用有上限的流读取，例如配置最多 64 KiB，超过直接使用系统默认语言。限制实际读取量，避免仅检查一次文件长度后仍无限读取被替换/增长的文件。增加超限、超深 JSON 和读取失败的回退检查。

### S5：驱动不返回时，操作锁和忙碌状态不能恢复

位置：`src/BatteryCharge.App/EnergyDevice.cs:40`；`src/BatteryCharge.Core/ChargeController.cs:73`、`:96`；`src/BatteryCharge.App/MainForm.cs:409`、`:625`。

`DeviceIoControl` 使用同步模式，没有超时/取消机制。外层 `Task.Run` 避免阻塞 UI 线程，但不能令未返回的驱动调用结束。控制器会一直持有串行锁，界面保留忙碌状态，刷新、切换功能和正常退出可能持续不可用。

“最多验证 12 次”仅限制已经返回的查询次数，不限制单次查询的等待时间。此项是驱动故障或异常设备条件下的可靠性问题，没有证据证明普通外部程序能经由本应用直接触发驱动挂起。

建议：先核验驱动是否支持可取消 I/O；必要时隔离到辅助进程并设置可恢复的超时/故障状态。仅用 `Task.WhenAny` 返回超时并释放锁不安全：原生操作可能继续进行，后续写入会破坏原有串行保证。界面恢复、句柄释放和超时后的禁止写入需要一起设计。

### S6：发布工作流的供应链权限可以缩小

位置：`.github/workflows/build.yml:21`、`:31`、`:34`、`:54`、`:63`、`:92`。

Action 引用使用 `@v7`、`@v6` 等可变标签；Windows 构建 job 从检出、检查到发布全程拥有 `contents: write`，并没有关闭 checkout 凭据持久化。上游 Action 或执行代码一旦被控制，会拥有超出编译需要的仓库写入能力，可能污染发布。

当前只在 tag 推送和手动触发时运行，没有发现自动执行普通外部 PR 的路径。此项是供应链加固问题，不代表已经发生令牌泄漏，也不代表普通 fork PR 可以直接取得写权限。

建议：Action 固定到核实过来源的完整提交 SHA，checkout 设置 `persist-credentials: false`，构建 job 保持只读，把必要的 `contents: write` 放到只负责发布的最小 job，并明确校验制品来源。[GitHub 官方安全说明](https://docs.github.com/en/actions/reference/security/secure-use)支持固定 SHA 和令牌最小权限策略。

现有 UI 检查允许失败后继续发布，是已明确选择的发布策略；这本身不属于安全漏洞，基础行为检查仍会阻止失败版本发布。

## 其他权限和功能限制

1. `StartupManager` 使用当前进程的 `WindowsIdentity`。普通账户通过 UAC 输入另一管理员账户凭据时，注册对象是提升后账户，不是原始桌面账户；遗留配置目录也来自提升后账户。可能表现为普通账户登录时不自动启动。代码路径明确，但需在 Windows 双账户环境验证实际体验。
2. 旧目录中的程序还在运行时，从新目录双击 EXE 会激活旧实例。路径检查仍比较旧实例自身路径与任务路径，二者可以一致，因此不会提示用户刚双击的新目录。退出旧实例后从新目录启动才能检查新进程路径。这是现有单实例行为带来的功能限制，不能把它当成文件完整性检测。
3. 程序只协调自身实例。联想原有软件或其他驱动客户端仍可能同时改写状态，导致验证失败或最后写入者覆盖前者；应用的互斥锁无法强制其他客户端遵守。

有利的设计包括：任务 XML 使用 `XElement` 构造，路径特殊字符正确转义；任务修改/删除前校验归属标记和账户 SID；不保存任务密码；配置只接受两种语言值；驱动调用使用固定设备名和 4 字节请求/响应，查询验证返回长度；充电操作串行并在写入后查询真实状态；清理非递归且约束临时文件命名。

本次审查未发现应用自身的网络监听、远程控制接口、任意命令执行入口或可由配置提供的驱动控制码。任务归属标记是防误操作标识，不是密码或签名，真正的任务访问控制仍依赖 Windows ACL。

尚未验证真实 Windows 权限边界、单实例对象 ACL、NTFS junction 攻击链、发布文件签名、仓库线上保护规则及实际运行时安全更新。联想 `EnergyDrv` 属于外部内核驱动，未审计其二进制或设备 ACL；其他程序是否能直接利用该驱动，需要结合机器上的驱动版本和权限另行判断。

建议修复顺序：先处理 S1/S2 的目录与权限边界，再修复 S3 和 S4；随后缩小 CI 写权限，并设计 S5 的超时恢复。增加针对安全边界的回归检查后，再在 Windows 上进行权限与多会话验证。
